# Channel event journal storage

The host supplies an absolute `ChannelIngressStorage.journal_path` in a persistent directory. The directory must be private to the process account and reside on an encrypted-at-rest volume. The runtime validates existing storage and never changes permissions to adopt an existing shared directory. `create_event_journal_directory` creates a new private directory; it returns `AlreadyExists` instead of repairing or adopting an existing path. Hosts must provision compliant storage before starting ingress.

On Unix, the directory has no group or other access (mode 0700), and journal artifacts have no group or other access (mode 0600). On Windows, the directory and artifacts must be owned by the current process account, have a non-null DACL, and grant access only to that account, LocalSystem, or Administrators. Administrative operating-system principals are trusted; this is not isolation from an administrator. New directories and files receive explicit protected DACLs before any content is written. Windows storage must support persistent ACLs. Reparse points in the directory chain, reparse-point artifacts, unsupported ACL entries, and alternate data streams are rejected. Path components that Win32 normalization would map to another object, such as a name ending in a period or space or a DOS device name with or without an extension, are rejected before anything is created. An existing artifact is used only if its canonical path also passes these checks, so an 8.3 short name cannot select a protected `.agent-shell` entry. An inherited ACL is acceptable only if its grants meet the same private-access rule. A broad or foreign-owned directory fails clearly; the runtime does not silently grant permissions or alter the host's directory.

The journal contains one exact pending request and one exact accepted original, receipt, and effective cursor. Its permanent lockfile serializes cooperating processes. A replacement is written to a private sibling, synced, and closed before publication. The `atomicwrites` replacement operation uses an atomic rename and directory sync on Unix, and `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` on Windows. Publication errors are returned; the runtime never emits a pending original before successful publication and never advances its cursor after a failed accepted-head publication.

The synced accepted head is the retirement authority for a matching pending original. Physical deletion is checked reclamation after retirement. Unix also syncs the directory after deletion. Windows does not claim a per-directory flush or durable physical unlink: a deleted pending file may survive a power loss, and restart reconciliation discards it without re-emitting or waiting for another receipt when it exactly matches the accepted head. Unrenamed temporaries are not authoritative and are checked before reclamation. A conflicting or unreadable artifact fails closed instead of being discarded.

Durability depends on the filesystem, storage device, and operating system honoring their sync and write-through operations. Microsoft documents that `MOVEFILE_WRITE_THROUGH` does not return until the file is moved on disk, and explicitly guarantees a flush only for a move performed as a copy and delete. A journal replacement stays in one directory, so it is a rename whose durability rests on the filesystem's handling of that flag. Microsoft does not document `MoveFileExW` replacement as atomic; recovery therefore validates whichever complete artifact it finds and never trusts an unrenamed temporary. Another process holding a journal file open without delete sharing, such as a scanner, can make a replacement or deletion fail; the runtime returns that error without bypassing it, and the unchanged pending original or provider message is delivered by a later attempt or replay. The runtime does not flush an entire Windows volume, require administrative volume handles, promise secure erasure, or provide application-layer journal encryption. A successful filesystem test demonstrates publication, validation, and recovery behavior; it is not a power-loss test of a storage device.

`atomicwrites` owns the platform-specific synced replacement operation. The Windows-only `windows-sys` dependency provides Microsoft's maintained ACL, account-token, file-creation, and reparse-point APIs. No environment override can disable privacy checks. The pending and accepted wire formats and host receipt contract are unchanged.
